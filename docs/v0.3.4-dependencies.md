# v0.3.4 依赖监控与 Redis 熔断

> 状态：实现、自动化回归和真实故障验收已完成；完整 `v0.3.4` 尚未完成。本批须经用户实际体验确认后才能提交或推送。

## 依赖探针

新增管理员接口 `GET /api/system/dependencies` 和顶部“系统监控”页面。MySQL、ClickHouse、Redis、MinIO、Kafka、Flink 分别独立探测并报告：

- `ok`、`disabled`、`unavailable`；未启用不等于故障。
- 本次探测耗时、探测方式和异常类型；不返回地址、账号、密码或内部异常正文。
- MySQL/ClickHouse 使用 `SELECT 1`，Redis 使用 `PING`，MinIO 使用健康端点，Kafka 获取元数据，Flink 查询作业概览。
- 所有探测有界超时并并行执行；该接口用于监控，不替代原有业务 readiness，也不修改业务数据。

页面同时展示共享限流/租约与目录缓存的熔断状态、连续失败数、短路次数和恢复等待。普通账号和服务身份不能借此获得管理权限。

## Redis 熔断

新增线程安全熔断器，默认连续失败 3 次打开，30 秒后进入半开并只允许一个恢复探测；成功后自动闭合，失败则重新打开。Compose 可通过 `REDIS_CIRCUIT_FAILURES` 和 `REDIS_CIRCUIT_RECOVERY_SECONDS` 配置。实测发现 5 秒短于本机部分 DNS 失败耗时，会过早发起下一次探测，因此默认窗口调为 30 秒。

覆盖范围：

- `RedisJsonCache`：打开时直接回源，不在同一次读取的 get/set 中重复尝试失效 Redis。
- `SharedLimiter`：普通读取/查询使用既有的每实例受限降级；管理、登录和写操作继续失败关闭。
- `ConnectionLeases`：WebSocket 与回放计算租约在打开时明确失败，不静默转为不受控的本地共享额度。

熔断只减少重复故障调用，不改变主存储事实源，不把缓存空值当作空业务结果，也不承诺 Redis 数据不丢失。

## 真实验收

`server/benchmarks/redis_circuit_acceptance.py` 使用隔离应用和可丢弃 Redis：停止并重命名 Redis 使原 DNS 消失，检查读取降级、写入 503 和熔断状态，再以原名新容器恢复并确认自动闭合。容器只停止和重命名，不删除。

真实演练使用隔离库中的 41,413 条科技帖子：

- 故障前查询 0.031 秒；DNS 消失后的前三次请求分别约 29.016、13.047、4.031 秒，说明熔断不能消除建立失败阈值所需的系统等待。
- 30 秒窗口内第四次读取少于 0.001 秒并返回相同 41,413 条记录，响应为 `local-degraded`；写操作约 0.016 秒返回 503 `rate_limit_unavailable`，没有静默放开。
- 打开时限流/租约熔断记录 3 次短路，缓存记录 5 次短路；恢复后读取约 0.047 秒并回到 `redis` 模式，两个熔断器自动闭合，Redis `PING` 约 5.905 毫秒。
- 报告位于忽略目录 `server/data/benchmarks/redis-circuit-acceptance.json`。
- 正式环境六项依赖最终均为 `ok`；Kafka 使用真实元数据探测。正式前端、readiness 和认证状态均为 HTTP 200。用户实际体验确认前本批不提交或推送。
