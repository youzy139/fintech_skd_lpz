# v0.3.4 回放持久化、恢复与结果补拉

> 状态：实现、自动化测试、真实后端重启和 Chrome 验收已完成，并已通过用户体验确认。完整 `v0.3.4` 尚未完成，不创建版本标签。

## 1. 持久化边界

新增 `server/app/services/replay_store.py`，使用现有 `database_path` 指向的 SQLite 数据库，不修改原始数据表：

- `replay_sessions`：会话模式、状态、日期范围、速度、已完成位置、运行 ID、Flink 作业 ID、Savepoint、恢复状态和完整快照。
- `replay_results`：以 `(session_id, sequence)` 为主键保存逐日结果和事件日期。
- `replay_operations`：保存幂等键、请求摘要和首次响应；同一键用于不同请求会被拒绝。
- `replay_metadata`：保存当前会话指针。

结果和会话快照在同一 SQLite 事务中提交。`processed_days` 现在只表示已成功保存的结果日，不再把正在等待输入的日期计为完成。服务关闭时，未完成游标回滚到最后一个已保存结果，避免重启后跳过数据。

## 2. 重启恢复口径

- 后端启动时重新载入会话和最新结果。运行中或已暂停的未完成会话统一呈现为“可恢复暂停”，不会在用户不知情时自动推进。
- 用户点击继续后，保留原 `run_id`，恢复计数增加。系统先根据原始行情确定性重建已保存日的模型内部状态，再从下一个未保存日期创建通道并运行。
- 已保存结果直接读取，不因 WebSocket 断线而重新执行模型；后端恢复时的模型内部重建不等于重新生成历史结果消息。
- Flink 恢复会创建新的作业 ID，保留原运行 ID 和最近 Savepoint 证据。已完成会话重载后保持完成，不启动新作业。
- 从头重开会生成新运行，并清空该会话旧结果序列；前端通过重开代次忽略上一轮尚未完成的补拉。

当前恢复是单后端实例的持久化恢复，不是多实例选主或高可用。模型内部重建需要真实计算时间，不能描述成毫秒级快照恢复。

## 3. 补拉与幂等接口

- `GET /api/replay/sessions/{id}/results?after=0&limit=100`：按序列升序返回缺失结果，包含 `next_sequence` 和 `has_more`；单页上限 100。
- `replay_day` WebSocket 消息增加 `sequence`；快照增加 `latest_sequence` 和 `recovery`。
- 前端记录最后序列，WebSocket 断开后每秒尝试重连并补拉；重复或较旧序号被忽略。页面显示结果序列、恢复状态、恢复次数和模型重建耗时。
- 创建、开始、暂停、继续、倍速和重开接受可选 `Idempotency-Key` 请求头。重复请求返回首次响应，同一键对应不同参数返回 422；开始、暂停和继续对已经处于目标状态的操作也不会重复创建后台任务。

- 后端 70 项测试通过，分支覆盖率 74.18%；前端 11 项测试及生产构建通过。
- 跨应用实例测试覆盖完成结果重载、结果分页、可恢复暂停、模型重建、幂等创建和重复继续。
