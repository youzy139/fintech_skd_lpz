## 基准与边界

新增 `server/benchmarks/websocket_user_performance.py`，使用临时合成数据、101 个独立 observer 用户及 JWT 会话、真实 Uvicorn 和同一两日历史回放：

- 默认连接上限 100 与显式上限 128 分开测量；端口固定 18000，被占用时报错，不自动换端口。
- 记录快照和逐日推送延迟，推送延迟使用结果 UTC `replay_time` 到客户端收到消息的时间差。
- 一名用户在第一日后断开，使用 REST `after=1` 补拉第二日，再重连核对完成快照。
- 慢消费者不读取期间，由 8 个独立分析员账号产生 110 次速度状态更新，保持每账号每分钟 20 次控制配额不变；随后检查 100 条队列、最新状态及 REST 两日结果。
- 初始快照直接发送，不进入 100 条待发送队列；慢消费者验收不要求该直接快照被挤出，而要求队列保持最新状态且结果可补齐。

这不是 101 个同时运行的回放：只有一个计算会话，回放计算租约默认最多 2 个不变。也不是 Nginx、真实 Redis 租约、多实例或公网验收。

## 实测结果

| 场景 | 结果 |
| --- | --- |
| 每服务上限 100 | 100 个连接成功，第 101 个以 `4429` 拒绝；没有推送样本，不能算延迟通过 |
| 每服务上限 128 | 101 个独立用户全部连接，拒绝数 0 |
| 推送延迟 | 200 个样本，p50 **14.509ms**、p95 **22.590ms**、p99 **23.592ms**、最大 **24.591ms** |
| 建连与首个快照 | p95 **127.359ms**；这是连接初始化，不冒充逐日推送延迟，也不是页面加载指标 |
| 断线补拉 | REST 第二日 sequence=2，重连快照 latest_sequence=2 且 completed |
| 慢消费者 | 110 次状态更新后队列 100 条，最新 speed=2；REST 结果为 1、2，补拉通过 |

在 128 上限、单机单进程和本地租约条件下，本批暂定“独立用户 >100 且推送 p95 <100ms”检查**通过**。报告位于 Git 忽略的 `server/data/benchmarks/v051-websocket-128-slow.json`。

## 实现调整

- 本地与 Compose 默认 `WS_MAX_CONNECTIONS_TOTAL` 从 100 调整为 **128**，使默认部署支持超过 100 个独立订阅者；环境变量仍可覆盖。
- 每账号最多 3 条连接、租约续租/过期、超额 4429、Redis 故障 1013 和回放计算并发策略不变。
- 新增默认容量与可配置覆盖测试；真实 100/128 两档行为以基准报告为准。
