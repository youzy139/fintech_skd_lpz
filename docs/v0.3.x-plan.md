# MarketLens v0.3.x 阶段计划

> 文档性质：`v0.3.x` 分阶段计划。`v0.3.0` 和 `v0.3.1` 已在本地实现并完成真实 API、单节点 Kafka 与 Chrome 验收，后续小节仍是计划，不代表 Flink 或完整分布式系统已经实现。

## 1. 当前基线

- 当前远程验收版本为 `v0.3.0`；`v0.3.1` 已完成本地实现和真实验收，等待用户体验后推送。
- 1,046 个输入文件已全部入库，共 1,556,492 条逻辑记录；原始文件保持不变。
- 本地 SQLite 已实现分批导入、增量跳过、统计与标签回填、预聚合概览、日期索引、并发访问锁和服务端分页。
- 已有 39 个资产序列的行情特征、walk-forward 状态识别、规则预警、双通道真实历史回放和完整 Web 页面。
- Kafka 4.3.2 单节点 KRaft 已实际联通，支持日批次生产、消费去重、乱序缓存、重试和处理后位点提交。
- 后端 34 项测试、前端 9 项测试通过；当前总体分支覆盖率约 84.30%，高于竞赛要求的 30%。
- `v0.2.2`、`v0.2.3` 和 `v0.3.0` 均已通过用户验收并推送。

当前边界必须保留：现有系统不是完整分布式系统；Kafka 仅为单节点事件接入，Flink、MySQL/ClickHouse/Redis/MinIO、独立微服务、完整权限、LLM 助手和 Docker Compose 尚未实现。旧 `/ws/replay` 只回放预计算状态，新 `/ws/replay/{session_id}` 才是原始记录驱动的回放。

## 2. 阶段目标

`v0.3.x` 的核心目标是形成可验证的事件时间处理链路：

> 历史数据按事件时间分批到达 → 当日数据清洗与窗口聚合 → 特征更新 → 状态识别与预警 → 前端观察时间推进和结果变化

首先证明业务和时间口径正确，再替换为分布式组件。不得仅把预计算结果换一种播放方式，就声称完成真实回放或实时计算。

## 3. 时间与数据口径

1. **完整入库不等于模型可见未来。** 历史档案可以完整保存；回放计算只能读取当前事件时间及此前已经发布的数据。
2. **区分两个时间：** `event_time` 是数据自身的交易日期、公布时间或发帖时间；`replay_time` 是系统实际处理这条记录的时间。
3. **窗口分开定义：** 接入和 Flink 聚合使用 1d 窗口；波动率、动量、相关性和模型训练继续使用明确的滚动历史窗口。
4. **不同资产交易日历不强行对齐。** 某日没有观测不代表缺失填充为前值；需要计算时再使用已声明的口径。
5. **宏观数据按公布时间进入。** 不能把统计期日期误当作当时已经可得的发布日期。
6. **文本按自身时间进入。** 新闻、社媒、公众号和研究摘要不得提前用于当日之前的状态或预警。
7. **标签只是检索元数据。** 当前确定性标签不等于情绪因子，不能直接作为金融结论。

## 4. 版本拆分

### v0.3.0：本地真实历史回放闭环

先不引入 Kafka/Flink，使用现有 Python 和 SQLite 证明完整业务链路。

- 实现独立回放时钟和会话状态：待开始、运行、暂停、完成、失败。
- 支持选择开始/结束日期、逐日推进、暂停、继续、倍速和重新开始。
- 按 `event_date` 分批读取资产行情，并保留文本和宏观事件的扩展接口。
- 每个回放日只处理当日及此前数据，保存事件时间、处理时间、输入范围和模型版本。
- 将当日特征、状态、预警和证据关联起来，不能只发送预计算状态。
- 提供回放控制 REST API 和状态/结果 WebSocket；保留旧接口直至替代链路验收。
- 前端增加回放控制条、当前事件日期、进度、速度和当日新增预警。
- 使用短历史区间完成真实 API 和 Chrome 验收。

验收重点：暂停后日期不推进，倍速只改变到达速度，改变回放范围不会引入未来数据，同一输入和配置可复现同一结果。

### v0.3.1：Kafka 事件接入

- 明确主题、键、分区、事件结构、生产者、消费者和失败重试。
- 历史回放生产者按事件时间发送，消费者执行与 `v0.3.0` 相同的处理逻辑。
- 保留事件时间与回放时间，验证重复消费、乱序和失败恢复。
- 不用 Kafka 代替原始数据持久化，不为了组件数量拆分无意义服务。

### v0.3.2：Flink 窗口与容错

- 使用 Flink 完成清洗、1d 窗口聚合和适用特征的增量计算。
- 明确事件时间、水位线、迟到数据和不同频率数据的处理口径。
- 实现 Checkpoint/Savepoint，验证故障后从一致位置恢复。
- 对比 Flink 与 `v0.3.0` 本地结果，防止分布式重写改变金融含义。
- 单独进行延迟和吞吐压测，未测之前不宣称达到竞赛性能指标。

### v0.3.3：分布式存储与部署基础

- MySQL：元数据、业务数据、规则和权限。
- ClickHouse：行情、特征、状态、预警等分析型时序数据。
- Redis：热特征、热点查询和必要的临时状态。
- MinIO：原始文件、研报和其他非结构化对象。
- 明确 ODS/DWD/DWS/ADS、分区、保留周期和数据血缘；原始层与派生层保持可追溯。
- 提供 Dockerfile 和 Docker Compose，逐步在干净环境验证一键启动、全部文件导入及核心链路。

### v0.3.4：服务治理与展示完善

- 根据实际边界拆分数据、特征状态和预警服务，评估 API Gateway。
- 增加认证授权、数据权限、分布式限流和缓存。
- 完善回放看板、状态热力图、预警证据和运行监控。
- 形成性能测试和故障恢复报告。

## 5. 恢复开发时的第一项任务

从 `v0.3.0` 开始，不先搭 Kafka：

1. 在 `market_core` 定义纯领域回放时钟、逐日输入包和回放结果，不依赖 FastAPI。
2. 在 `server` 实现按日期查询输入、回放会话组装和控制 API。
3. 在 `web` 增加回放控制和当日结果展示。
4. 先用一个小型固定数据集写单元与集成测试，再运行真实历史区间。
5. 验证后更新 README、架构文档和 `AGENTS.md`，本地提交并创建对应版本标签；用户实际体验并明确确认后才推送。

## 6. 测试与验收要求

- 回放时钟：开始、暂停、继续、倍速、结束、重开和非法状态转换。
- 时间正确性：任何一天都不能读取未来记录；宏观值按公布时间可见。
- 数据正确性：不同交易日历、空日期、重复记录、迟到数据和缺失值有明确行为。
- 结果正确性：相同输入和配置可复现；状态与预警能追溯到当日输入和特征。
- 服务与页面：REST 控制、WebSocket 推送、断线、错误状态、加载状态和前端操作。
- 性能：在对应版本单独测量，不把局部查询耗时当作端到端实时性能。
- 最终回归：后端完整测试与覆盖率、前端测试与构建、真实 API 和真实 Chrome 缺一不可。

## 7. 不在本阶段核心链路中的内容

- 不让 LLM 决定市场状态、预警级别或回放结果。
- 不做自动交易或由 LLM 自由生成资产配置权重。
- 不在真实回放尚未验证前，把主要精力投入 LLM 聊天页面。
- 不把部署 Kafka/Flink 本身当作业务闭环完成；必须验证数据、时间和结果。
- 不把 `v0.3.x` 描述为正式版。`v1.0.0` 仍需完整网页、核心 API、全链路、权限及 Docker Compose 等验收。

## 8. 本地恢复命令

```bash
# 后端
PYTHONPATH=".;server" PYTHONUTF8=1 C:/ProgramData/miniconda3/envs/fintech/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 前端，在 web/ 目录执行
npm run dev -- --host 127.0.0.1

# 后端测试
PYTHONUTF8=1 conda run -n fintech python -m pytest --cov=market_core --cov=server/app --cov-report=term-missing server/tests

# 前端测试与构建，在 web/ 目录执行
npm test && npm run build
```

访问 `http://127.0.0.1:5173/`。私有配置和运行数据库继续放在被 Git 忽略的 `server/config.json` 与 `server/data/`，不得把密钥写入文档或 Git。
