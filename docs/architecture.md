# 总体架构设计

## 1. 文档状态

本文同时记录最终架构目标与 `v0.1.0` 当前实现。第 4～7 节中的分布式组件属于目标架构；第 8～10 节记录已经落地的仓库边界、技术栈和后续工作，阅读时不得将目标组件误判为已经部署。

## 2. 项目定位与边界

项目定位为：

> 以数据管道和市场状态模型为核心，以 Web 监控平台为交付主体，以 LLM 投研助手为增强模块。

核心业务链路为：

> 状态判断 → 预警决策 → 分析建议

- 状态判断：识别趋势、波动、风险偏好和资产联动等市场环境。
- 预警决策：根据可配置规则和异常检测结果，决定是否预警及预警级别。
- 分析建议：解释判断依据，关联历史时期、新闻和宏观事件，给出后续关注点。

第一版不以自动交易、多 Agent 自由协作或通用 RAG 聊天应用为主体。资产配置只能作为后续受约束的辅助分析能力，不由 LLM 自由生成数值权重。

## 3. 设计原则

1. 数据平台是地基，市场状态模型是核心，Web 平台是主要交付。
2. 数值特征与状态由数学模型计算，预警由确定性规则和异常检测产生。
3. LLM 负责文本结构化、证据整合和自然语言解释，不直接篡改核心结果。
4. 离线训练与在线识别分离，历史验证严格避免未来数据泄漏。
5. LLM 是可替换、可降级的增强模块，不成为核心链路的单点依赖。
6. 优先跑通完整闭环，再增加 RAG、资产配置和其他创新功能。

## 5. 核心处理流程

1. 多源适配器读取行情、指标、事件与文本，保留来源文件、原始日期和必要的采集时间。
2. 原始文件与非结构化内容保存到 MinIO，元数据写入 MySQL，结构化记录进入后续数据链路。
3. Kafka 按数据类型传递事件，解耦接入与计算，并支持失败重试。
4. Flink 按事件时间完成清洗、标准化、日窗口聚合和特征更新。
5. 在线模型加载已训练的指定版本，输出市场状态和主要判断依据。
6. 规则引擎结合状态变化与异常检测结果，生成可解释的预警。
7. 特征、状态和预警写入 ClickHouse，热点结果进入 Redis，并通过 WebSocket 推送。
8. LLM 按需查询状态、特征、预警和相关文本，生成摘要不参与实时计算关键路径。

## 6. 模块职责

### 6.1 数据接入层

- 为不同文件类型提供独立适配器。
- 对大型 CSV 使用标准解析器流式读取，处理引号与内嵌换行。
- 对 Excel 处理全部目标 sheet。
- 检查完整性、一致性、时效性和记录数。
- 保存导入批次、来源、失败原因与重试状态。
- 所有原始文件必须入库，派生数据与原始层分离。

### 6.2 实时处理层

- 使用 Kafka 解耦数据生产与消费。
- 使用 Flink 完成清洗、窗口聚合、特征计算、状态识别和预警。
- 保留事件时间，处理乱序和迟到数据时明确口径。
- 配置 Checkpoint/Savepoint，支持故障恢复。
- 不在低延迟关键路径中同步调用 LLM。

### 6.3 模型层

离线训练负责历史特征构造、特征选择与降维、模型训练、状态画像、回测和模型版本登记。

在线识别只使用当时可得的数据和已登记模型，输出状态、置信度或相似度、模型版本及主要贡献特征。训练和回测按时间切分，不能使用当时尚未公布的宏观值或未来文本。

### 6.4 存储层

- MySQL：数据目录、导入批次、用户权限、预警规则、特征元数据和模型版本。
- ClickHouse：标准化行情、宏观序列、特征、状态、预警和回测等分析型时序数据。
- Redis：热点查询、热特征、实时推送所需的临时状态与限流信息。
- MinIO：原始文件、研报摘要和其他非结构化对象。

存储设计需进一步落实 ODS/DWD/DWS/ADS 分层、时序分区、索引和生命周期策略。

### 6.5 服务层

- API Gateway：统一入口、认证、限流与路由。
- 数据服务：数据目录、行情、指标、文本和质量报告查询。
- 特征与状态服务：特征、当前状态、历史状态和模型解释查询。
- 预警服务：预警列表、规则配置、处理状态和回测结果。
- 实时推送服务：通过 WebSocket 推送状态变化与预警。
- 用户与权限能力：认证和数据权限，可作为独立服务或边界清晰的共享模块。

提供 RESTful API、GraphQL、WebSocket 和 OpenAPI 文档。服务数量以职责清晰和可维护为准，避免无意义拆分。

### 6.6 LLM 分析助手

提供每日市场摘要、状态切换解释、预警说明、相关文本检索和自然语言问答。

助手只能通过受控接口获取数据，例如：

```text
get_market_state(date)
get_feature_changes(date)
get_active_alerts(date)
get_related_events(date)
search_research_documents(query)
```

LLM 不得直接修改原始行情、特征、状态标签、已触发预警或模型版本。其不可用时，数据接入、状态识别、预警和看板仍须正常运行。

### 6.7 Web 平台

第一版规划以下页面：

1. 市场总览：当前状态、资产表现、风险等级和最新预警。
2. 市场状态分析：状态时间轴、热力图、切换记录和贡献特征。
3. 特征分析：收益率、波动率、动量、相关性及特征重要性。
4. 预警中心：预警列表、规则配置、触发证据和历史回测。
5. 数据中心与 AI 助手：数据覆盖、导入状态、质量报告、文件检索和市场问答。

## 7. 历史数据回放

赛题以历史数据为主，实时链路通过历史回放演示和验证：

- 按原始事件时间逐日或加速发送数据。
- 数据进入与真实接入一致的 Kafka/Flink 链路。
- 前端持续接收状态和预警更新。
- 支持暂停、调速和选择回放范围。
- 分别保存事件时间与回放时间。

回放只模拟数据到达过程，不得把未来数据提前用于状态识别。

## 8. 当前仓库边界

```text
market_core/
  domain/              # 资产、质量和预警领域对象
  ingestion/           # 真实资产目录与 CSV 接入
  models/              # 特征、walk-forward 状态模型与预警
server/
  app/api/             # API 模块边界
  app/core/            # 服务配置
  app/services/        # 应用服务组装与 SQLite 快照
  app/main.py          # REST、GraphQL、WebSocket 入口
  tests/               # 核心与接口测试
  config.example.json  # 无密钥配置模板
  config.json          # 本地私有配置，Git 忽略
  data/                # 本地运行时数据，Git 忽略
web/                   # React + TypeScript + ECharts 前端
docs/                  # 架构和后续数据、模型文档
```

核心算法不依赖 FastAPI，可以脱离服务层独立训练和回测。`server` 只负责配置、运行存储、服务组装和对外接口，不承载领域算法。

## 9. 当前技术栈与 LLM 配置

- 本地环境为 Conda `fintech`，Python 3.12；依赖见 `environment.yml` 和 `requirements*.txt`。
- 服务层使用 FastAPI、Strawberry GraphQL 和 Uvicorn，本地快照使用 SQLite。
- 前端使用 React、TypeScript、Vite、ECharts 和 Vitest。
- 模型使用 NumPy、pandas、scikit-learn，按滚动历史窗口执行标准化、PCA 和 KMeans。
- Conda 用于本地开发，Docker Compose 用于完整系统交付与验收，两者不能相互替代。
- LLM 暂定使用 `deepseek-v4.1flash`，API 基础地址和模型可用性尚未验证，当前未接入核心链路。
- 私钥可通过本地 `.env` 或后续 `server/config.json` 的忽略配置注入；不得提交真实密钥。
