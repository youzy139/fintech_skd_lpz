# ADR-001：保留 Nginx + FastAPI 统一入口

- 日期：2026-11-02
- 状态：本批实现与工程验证完成，已通过用户体验验收；不代表 v0.3.4 完成。
- 范围：统一接入选型与契约修复；认证、权限和分布式限流另批实施。

## 背景与竞赛约束

当前 Nginx 提供静态页面和同源反向代理，FastAPI 主后端组合数据、特征状态与历史预警服务。主后端还承担 GraphQL 聚合、OpenAPI、错误规范和 readiness，远程模式不创建第二份模型与回放管理器。

赛题“接口服务与可视化平台”将 API Gateway 写在**架构参考**中；统一要求另列微服务、三种接口协议、Redis + Caffeine、JWT/OAuth2、API 限流和 OpenAPI。保留现有接入方案不等于满足所有统一要求：Caffeine、认证权限及分布式限流仍未实现，必须继续补齐。不能把 Python 缓存或 Nginx 反向代理包装成这些能力。

## 备选方案

| 方案 | 调用路径与收益 | 本项目成本与限制 |
| --- | --- | --- |
| A：增强现有入口 | Nginx → FastAPI → 对应服务；沿用聚合、错误与回放契约，不增服务 | Python 入口仍需实现跨协议授权、Redis 限流和审计；Caffeine 需另定实际职责 |
| B：Nginx 直接分流 | Nginx → 数据/特征/预警；GraphQL、系统接口、OpenAPI 留在 FastAPI；部分查询少一次 HTTP | 真实停服返回 HTML 502，与当前 JSON 503 不同；限流作用域分散，需重新统一错误、权限与配置 |
| C：专用成熟网关 | 可评估 Spring Cloud Gateway、APISIX 或 Kong，将入口路由及通用策略集中 | 仍要保留业务聚合与服务内授权；引入运行时、配置、升级和故障面。未部署这些产品，不能声称其性能或鉴权已验证 |

方案 B 使用已有 Nginx 1.27.4 镜像执行了真实对照，是分流可行性实验，**不是方案 C 的产品压测替代品**。候选配置位于 `server/benchmarks/gateway-candidate.conf`，仅用于本地评估，不加入默认 Compose。

## 决策与证据

本阶段选择 **A**，保留 Nginx + FastAPI 单入口；不新增专用网关进程。真实两日回放、幂等创建、WebSocket、补拉与查询对照通过，现有入口在三项下游停服时保留结构化 503、请求 ID 及故障隔离。候选分流虽减少部分查询延迟，却需要重做错误规范、统一策略和运维验证；小样本不足以证明正式性能收益。数据和完整边界见 [入口评估报告](v0.3.4-gateway-evaluation.md)。

本批修复：特征与预警代理白名单透传 `Retry-After`、`WWW-Authenticate`、`Allow` 和原 Content-Type，保留状态码与原始正文；不转发 hop-by-hop 或内部私有头。Nginx 为 `/docs` 与 `/openapi.json` 增加准确路由，避免被 SPA 回退替换为 HTML。传递认证挑战不代表已实现认证。

## 后续与重评条件

下一批先定义观察者、分析员、管理员的操作与数据范围矩阵，再选择 JWT/OAuth2 实现；REST、GraphQL 和 WebSocket 必须执行同一服务端策略。随后落实审计、Redis 原子限流及断连/失效策略。

Caffeine 是显式待办：结合有实际需求的 Java 能力，说明缓存对象、版本、容量、过期和失效机制，与 Redis 分工，并验证故障行为；不得为引入库而缓存金融判断或绕过授权。需要动态路由、多实例集中治理、身份插件，或压测证明入口成为瓶颈时，重新评估方案 C，并对具体产品跑同一组契约与故障用例。

## 回退与验收

默认 Compose 拓扑不变。代码回退时只撤销本批两个代理与共享响应头模块、Nginx 文档路由，重建后端/前端；重建后端使地址变化时须重建或重启前端，确保 Nginx 重新解析上游。不得删除数据卷、原始数据或更改模型。临时候选容器用 `docker rm -f marketlens-gateway-eval` 清理。

用户已明确确认本批验收通过，可提交本批变更；不创建版本标签，完整 v0.3.4 仍在开发。
