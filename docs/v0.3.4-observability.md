# v0.3.4 首批契约、观测与性能基线

> 状态：首批实现、Flink 连续回放修复与真实验收已完成，并已通过用户体验确认。整个 `v0.3.4` 尚未完成，不创建版本标签。

## 1. 本批实现

- REST 按 `system`、`market`、`data`、`replay` 提取到 `server/app/api/`，GraphQL 和 WebSocket 仍由 `main.py` 组装。这是模块边界，不是独立微服务。
- 所有 HTTP 响应返回 `X-Request-ID`。错误保留原 `detail`，同时增加 `error.code`、`error.message`、`error.request_id`；参数校验、404、409、429 和 500 使用统一契约，500 不回传内部异常正文。
- JSON 请求日志记录请求 ID、路由模板、状态码和耗时，不记录查询参数或请求正文。回放日志使用会话 ID、运行 ID 和事件日期关联。
- `/api/health` 继续表示进程存活；`/api/health/ready` 检查市场快照和目录主读是否可用。它尚不是 MySQL、MinIO、Redis、Kafka 等全部依赖的独立探针。
- `/api/system/metrics` 提供当前进程的请求数、错误数、WebSocket 连接、回放会话，以及每个路由最近 512 个样本的 p50/p95/p99。指标不跨实例、不持久化，也未接入 Prometheus。
- 回放快照和页面增加运行 ID、模型初始化、通道初始化、逐日输入等待、模型计算、结果确认，以及 Kafka 生产、消费等待和位点提交耗时。无测量值时显示未知，不填造零值。

## 2. 基准方法

固定条件：

- Windows 11、24 个逻辑 CPU、Docker Desktop、分布式目录主读。
- 2026-04-27 至 2026-04-30，共 4 个事件日、154 条资产观测。
- 本地、Kafka、Flink 使用相同输入、模型和 10 倍播放速度；REST 状态轮询间隔 0.3 秒。
- 每种模式执行 3 轮，报告 p50、p95、最小值和最大值；p95 使用最近秩口径，小样本不等于正式性能验收。
- 本地与 Kafka 的第一轮标为 cold，后两轮标为 warm，报告保留分组结果。
- Flink 每轮停止旧作业，将专用测试消费组定位到最新输入位点，再启动全新作业。原始消息不删除。这里的 cold 指新作业状态，不把容器构建和集群启动时间计入回放耗时。
- 整轮耗时从开始回放计到完成，包含模型初始化、通道处理、模型计算、播放间隔和轮询开销；不包含镜像构建和集群启动。吞吐量为 154 条观测除以整轮秒数。
- 最终结果的日期、状态、特征和预警必须结构一致，浮点比较容差为 `1e-12`，用于容纳 Kafka JSON 往返造成的最后位舍入；不按墙钟处理时间比较。

复现命令：

```bash
PYTHONPATH=".;server" PYTHONUTF8=1 python -m app.services.replay_benchmark \
  --base-url http://127.0.0.1:8000 \
  --start 2026-04-27 --end 2026-04-30 \
  --modes local,kafka --runs 3 --speed 10 \
  --output server/data/benchmarks/replay-v034-local-kafka.json
```

Flink 冷环境按上述隔离步骤逐轮准备后，以 `--modes flink --runs 1` 分别生成三份报告。原始报告保存在被 Git 忽略的 `server/data/benchmarks/`。

## 3. 实测结果

| 模式 | 整轮 p50 | 整轮 p95 | 首个结果 p50 | 吞吐量 p50 |
| --- | ---: | ---: | ---: | ---: |
| 本地直连 | 17.672 s | 17.922 s | 13.594 s | 8.714 条/s |
| Kafka | 17.906 s | 18.078 s | 13.781 s | 8.600 条/s |
| Flink（全新作业） | 21.781 s | 23.453 s | 17.922 s | 7.070 条/s |

三轮最终结果均通过容差一致性核对。

四日累计阶段耗时的三轮中位数：

| 模式 | 模型初始化 | 输入等待 | 模型计算 | 结果确认 |
| --- | ---: | ---: | ---: | ---: |
| 本地直连 | 12.164 s | 0.023 s | 5.077 s | 0.000018 s |
| Kafka | 12.356 s | 0.037 s | 5.157 s | 0.0035 s |
| Flink（全新作业） | 12.622 s | 4.336 s | 5.161 s | 0.000052 s |

这些数字说明：

1. 当前小样本下，模型初始化和逐日 Python 计算占据主要时间，不能只把慢归因于 Kafka 或 Flink。
2. Flink 的输入/窗口等待明显高于本地与 Kafka，但其测量还包含全新作业的处理环境差异，不能用单轮最快或最慢值概括。
3. 当前吞吐与竞赛目标的 `>10 万条/秒` 不是同一达成水平，不能宣称性能达标。本轮未采集完整 CPU、内存、GC 和资源曲线，`resource_usage` 明确标为 `not_collected`。
4. 本轮只建立基线，没有通过跳过窗口、关闭检查点、提前提交位点或读取未来数据提速。

## 4. 连续 Flink 回放缺陷与修复

基准过程中复现了独立正确性问题：首轮控制事件把全局水位线推进到处理时间后，后续历史事件全部进入 `marketlens.replay.late.v1`，正常输出缺失。失败复现的两轮共 4 个日批次全部进入迟到主题，正常主题为 0。

修复采用每次 `run_id` 独立作业，而不是让多个历史时间轴共享全局水位线：

- source 先过滤当前 `session_id + run_id`，再分配事件时间和水位线；每个运行使用独立消费者组。
- 后端通过 Flink 2.2.1 REST 的 `programArgsList` 参数数组启动作业，等待 RUNNING 和首个检查点后再生产，避免 latest 位点建立前发送首日。
- 控制事件使用最后事件日期加 3 天推进本运行水位线，不把历史行情时间改为处理时间。
- 完成或重开只停止本运行作业并生成 Savepoint；启动失败通过 PATCH 只取消新作业。
- 修复了 Flink 通道把结果主题误作作业输入主题的问题，并有单元测试防止回归。

真实验收结果：

- 同一集群连续两轮各 2 天均完成，正常主题各 2 条、迟到主题各 0 条，作业 ID 不同且均生成 Savepoint。
- 2026-04-27 至 2026-04-30 的本地、Kafka、Flink 最终结果在 `1e-12` 容差内一致；该轮分别为 16.781s、17.422s、24.375s。独立 Flink 仍慢，新增作业与首检查点等待是明确开销，不能宣称完成性能优化。
- 暂停继续、同会话重开和不同日期范围通过；重开使用新运行与新作业，最终结果一致。
- Savepoint 实际恢复为新作业，检查点 `restored` 计数为 1。
- 真实乱序输入产生 2 条正常结果，重复事件被去重，另一个超过容忍期的历史日期进入迟到主题 1 条。水位线按周期发射，测试在控制事件后等待传播再发送超迟事件。

原始报告位于被忽略的 `server/data/benchmarks/replay-v034-flink-independent-hot.json`、`flink-lifecycle-validation.json` 和 `flink-lateness-validation.json`。
