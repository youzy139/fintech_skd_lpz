# MarketLens v0.3.x 阶段计划

> 文档性质：`v0.3.x` 分阶段计划。`v0.3.0`～`v0.3.3` 已完成真实验收，后续小节仍是计划，不代表完整微服务或正式版能力已经实现。

## 1. 当前基线

- 当前版本为 `v0.3.3`，分布式存储、在线增量发布、Docker Compose 和干净空卷验收已完成并通过用户体验确认。
- 1,046 个输入文件已全部入库，共 1,556,492 条逻辑记录；原始文件保持不变。
- 本地 SQLite 已实现分批导入、增量跳过、统计与标签回填、预聚合概览、日期索引、并发访问锁和服务端分页。
- 已有 39 个资产序列的行情特征、walk-forward 状态识别、规则预警、三通道真实历史回放和完整 Web 页面。
- Kafka 4.3.2 单节点 KRaft 与 Flink 2.2.1 单 JobManager/TaskManager 已实际联通，支持日窗口、去重、迟到分流、检查点、Kafka 事务输出和 Savepoint 恢复；每运行独立作业已修复连续历史回放的全局水位线冲突。
- v0.3.3 阶段 A～E 已完成真实验收：默认八个容器和可选 Flink、全量对象回读、容器三通道、Nginx WebSocket、真实 Chrome、Redis 停服和故障恢复均通过；干净源码目录与全新空卷的一键启动、全量数据和回放复验也已通过。
- `v0.3.4` 当前后端 67 项测试、前端 10 项测试通过；总体分支覆盖率约 73.01%，高于竞赛要求的 30%。真实基准与连续回放验收见 [观测与性能基线](v0.3.4-observability.md)。
- `v0.2.2`、`v0.2.3`、`v0.3.0`～`v0.3.3` 均已通过用户验收并发布。

当前边界必须保留：现有系统不是完整微服务或高可用系统；Kafka 与 Flink 均为单节点验证环境。本地默认 SQLite，可显式切换 ClickHouse 主读，MySQL/MinIO 承担发布链路中的元数据与对象职责，Redis 可回源；独立微服务、完整权限和 LLM 助手尚未实现。旧 `/ws/replay` 只回放预计算状态，新 `/ws/replay/{session_id}` 才是原始记录驱动的回放。

## 2. 阶段目标

`v0.3.x` 的核心目标是形成可验证的事件时间处理链路：

> 历史数据按事件时间分批到达 → 当日数据清洗与窗口聚合 → 特征更新 → 状态识别与预警 → 前端观察时间推进和结果变化

首先证明业务和时间口径正确，再替换为分布式组件。不得仅把预计算结果换一种播放方式，就声称完成真实回放或实时计算。

## 3. 时间与数据口径

1. **完整入库不等于模型可见未来。** 历史档案可以完整保存；回放计算只能读取当前事件时间及此前已经发布的数据。
2. **区分两个时间：** `event_time` 是数据自身的交易日期、公布时间或发帖时间；`replay_time` 是系统实际处理这条记录的时间。
3. **窗口分开定义：** 接入和 Flink 聚合使用 1d 窗口；波动率、动量、相关性和模型训练继续使用明确的滚动历史窗口。
4. **不同资产交易日历不强行对齐。** 某日没有观测不代表缺失填充为前值；需要计算时再使用已声明的口径。
5. **宏观数据按公布时间进入。** 不能把统计期日期误当作当时已经可得的发布日期。
6. **文本按自身时间进入。** 新闻、社媒、公众号和研究摘要不得提前用于当日之前的状态或预警。
7. **标签只是检索元数据。** 当前确定性标签不等于情绪因子，不能直接作为金融结论。

## 4. 版本拆分

### v0.3.0：本地真实历史回放闭环

先不引入 Kafka/Flink，使用现有 Python 和 SQLite 证明完整业务链路。

- 实现独立回放时钟和会话状态：待开始、运行、暂停、完成、失败。
- 支持选择开始/结束日期、逐日推进、暂停、继续、倍速和重新开始。
- 按 `event_date` 分批读取资产行情，并保留文本和宏观事件的扩展接口。
- 每个回放日只处理当日及此前数据，保存事件时间、处理时间、输入范围和模型版本。
- 将当日特征、状态、预警和证据关联起来，不能只发送预计算状态。
- 提供回放控制 REST API 和状态/结果 WebSocket；保留旧接口直至替代链路验收。
- 前端增加回放控制条、当前事件日期、进度、速度和当日新增预警。
- 使用短历史区间完成真实 API 和 Chrome 验收。

验收重点：暂停后日期不推进，倍速只改变到达速度，改变回放范围不会引入未来数据，同一输入和配置可复现同一结果。

### v0.3.1：Kafka 事件接入

- 明确主题、键、分区、事件结构、生产者、消费者和失败重试。
- 历史回放生产者按事件时间发送，消费者执行与 `v0.3.0` 相同的处理逻辑。
- 保留事件时间与回放时间，验证重复消费、乱序和失败恢复。
- 不用 Kafka 代替原始数据持久化，不为了组件数量拆分无意义服务。

### v0.3.2：Flink 窗口与容错

- 使用 Flink 完成清洗、1d 窗口聚合和适用特征的增量计算。
- 明确事件时间、水位线、迟到数据和不同频率数据的处理口径。
- 实现 Checkpoint/Savepoint，验证故障后从一致位置恢复。
- 对比 Flink 与 `v0.3.0` 本地结果，防止分布式重写改变金融含义。
- 单独进行延迟和吞吐压测，未测之前不宣称达到竞赛性能指标。

### v0.3.3：分布式存储与部署基础

详细范围、迁移顺序与验收见 [v0.3.3 任务书](v0.3.3-plan.md)。阶段 A～E 及干净环境复验均已完成，等待用户体验与发布确认。

- MySQL：元数据、业务数据、规则和权限。
- ClickHouse：行情、特征、状态、预警等分析型时序数据。
- Redis：热特征、热点查询和必要的临时状态。
- MinIO：原始文件、研报和其他非结构化对象。
- 明确 ODS/DWD/DWS/ADS、分区、保留周期和数据血缘；原始层与派生层保持可追溯。
- 提供 Dockerfile 和 Docker Compose，逐步在干净环境验证一键启动、全部文件导入及核心链路。
- 保留 SQLite 与本地直连作为开发、算法回归和回退基线。

### v0.3.4：服务治理与展示完善

详细范围、实施顺序与验收见 [v0.3.4 任务书](v0.3.4-plan.md)。当前已启动“契约与观测”首批实施，尚未完成整个版本，未提交或推送。

- 根据实际边界拆分数据、特征状态和预警服务，评估 API Gateway。
- 增加认证授权、数据权限、分布式限流和缓存。
- 完善回放看板、状态热力图、预警证据和运行监控。
- 形成性能测试和故障恢复报告。
- 已知问题：Flink 在小数据、逐日历史回放中明显慢于本地直连。先记录生产、窗口、水位线、事务、消费和模型各阶段耗时，再减少固定等待并建立有界流水线；优化后仍须通过三通道一致性、乱序迟到与 Savepoint 验收。

## 5. 恢复开发时的第一项任务

`v0.3.3` 已完成并推送。`v0.3.4` 首批契约拆分、请求观测、回放计时、真实页面和三通道基准已完成，记录见 [首批观测与性能基线](v0.3.4-observability.md)，不要重复本轮工作。下一步依次为：

1. 修复同一 Flink 作业连续多轮回放的水位线/迟到问题，先做正确性，再做性能优化。
2. 实现回放会话与结果持久化、后端重启恢复和断线补拉。
3. 按任务书推进服务拆分、认证权限、分布式限流、缓存治理、预警证据和系统监控。
4. 核实宏观公布时间并接入部分宏观/文本证据，随后完成性能压测和正式交付材料。

当前远程为 `v0.3.3`，本地 `v0.3.4` 首批修改未提交或推送；必须等用户实际体验并明确确认。完整待办见 [v0.3.4 任务书](v0.3.4-plan.md#21-下次恢复时的待办)。

## 6. 测试与验收要求

- 回放时钟：开始、暂停、继续、倍速、结束、重开和非法状态转换。
- 时间正确性：任何一天都不能读取未来记录；宏观值按公布时间可见。
- 数据正确性：不同交易日历、空日期、重复记录、迟到数据和缺失值有明确行为。
- 结果正确性：相同输入和配置可复现；状态与预警能追溯到当日输入和特征。
- 服务与页面：REST 控制、WebSocket 推送、断线、错误状态、加载状态和前端操作。
- 性能：在对应版本单独测量，不把局部查询耗时当作端到端实时性能。
- 最终回归：后端完整测试与覆盖率、前端测试与构建、真实 API 和真实 Chrome 缺一不可。

## 7. 不在本阶段核心链路中的内容

- 不让 LLM 决定市场状态、预警级别或回放结果。
- 不做自动交易或由 LLM 自由生成资产配置权重。
- 不在真实回放尚未验证前，把主要精力投入 LLM 聊天页面。
- 不把部署 Kafka/Flink 本身当作业务闭环完成；必须验证数据、时间和结果。
- 不把 `v0.3.x` 描述为正式版。测试版允许分阶段补齐能力，但不得把未完成项写成已实现。

## 8. v1.0.0 正式版合规门槛

`v0.x` 不要求每个补丁都满足全部赛题交付条件；`v1.0.0` 前必须逐项实测并通过，不能以组件清单或计划书代替验收。

### 淘汰红线

- 干净环境 `docker-compose` 一键启动成功，系统核心功能完整可用。
- 不存在明显 SQL 注入、硬编码真实密码/密钥等安全漏洞；本地无密码示例不得用于正式部署。
- 核心代码、模型口径、时间窗口和数据流能够在答辩中解释，不能交付无法说明的生成代码。

### 核心功能

- 数据、特征状态、预警服务边界清晰，具备微服务或等效可独立部署实现。
- JWT/OAuth2 用户认证、数据权限、API 限流、Redis 缓存与 Caffeine 本地缓存落地。
- MySQL/ClickHouse/Redis/MinIO/Kafka/Flink 不只完成迁移或演示，按声明职责进入实际应用链路，并支持在线增量处理。
- 宏观和文本数据至少有一部分真正进入分析或证据链，公布/发布时间口径正确；预警规则可配置。
- REST、GraphQL、WebSocket、OpenAPI 和 React 平台完成端到端验收，历史回放不被描述成实时行情。

### 性能与稳定性

- 分别测量端到端 `<100ms`、吞吐 `>10 万条/秒`、特征 `<50ms`、状态识别 `<1s`。
- 测量 API `<50ms`、WebSocket `<100ms`、页面加载 `<2s`、并发用户 `>100` 和 Redis 热特征 `<10ms`。
- 只有真实报告支持时才宣称达标；未达标项必须继续优化或如实披露，不能隐藏本地/Flink 对照。
- 完成 Checkpoint/Savepoint、故障恢复、压测和资源利用验证。

### 交付材料

- 产品及技术方案 PDF（40 页以内），包括产品/技术架构、数据流程、技术选型、模型效果和应用效果论证。
- ER 图、数据流图、统一数据模型、数据质量报告及必要的 ADR。
- Git 仓库含 Dockerfile、Compose、README、API 文档和单元测试，分支覆盖率保持高于 30%。
- 5 分钟以内 MP4 演示视频，1080p，包含功能演示和架构说明。
- 保留 AI 协作过程、版本记录与产出把控证据，满足使用透明度要求。

只有上述红线、核心功能、性能验证和交付材料全部完成后，才能发布 `v1.0.0`。后续 `v1.x` 的补丁不能用来掩盖首发版本缺失的强制要求。

## 9. 本地恢复命令

```bash
# 后端
PYTHONPATH=".;server" PYTHONUTF8=1 C:/ProgramData/miniconda3/envs/fintech/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

# 前端，在 web/ 目录执行
npm run dev -- --host 127.0.0.1

# 后端测试
PYTHONUTF8=1 conda run -n fintech python -m pytest --cov=market_core --cov=server/app --cov-report=term-missing server/tests

# 前端测试与构建，在 web/ 目录执行
npm test && npm run build
```

访问 `http://127.0.0.1:5173/`。私有配置和运行数据库继续放在被 Git 忽略的 `server/config.json` 与 `server/data/`，不得把密钥写入文档或 Git。
