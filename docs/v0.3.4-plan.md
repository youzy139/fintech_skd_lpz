# MarketLens v0.3.4 任务书：服务治理、可观测性与性能优化

> 文档性质：后续实施计划，不代表相关能力已经实现或验收。本版本以 `v0.3.3` 的存储与部署验收为前置条件；本文档本身不创建版本标签。

## 1. 目标

在不改变市场模型和时间口径的前提下，把现有单体 API 演进为边界明确、可治理、可观测、可恢复的服务体系，并补齐回放与预警的证据展示。

本版本同时登记一个已知问题：**Flink 窗口在小数据、逐日历史回放中明显慢于本地直连**。优化必须先定位各阶段耗时，再减少等待和增加有效流水线；不得通过跳过窗口、关闭必要容错或读取未来数据换取表面速度。

## 2. 当前基线与边界

- 当前 REST、GraphQL、WebSocket 和简单进程内限流集中在 FastAPI 应用中，`server/app/api/` 尚未形成实际路由拆分。
- 回放会话和计算结果主要保存在当前后端进程内；Kafka/Flink 为单节点验证环境，尚无高可用能力。
- 前端已有市场、状态、回放、特征、预警、数据中心页面，但运行指标较少，预警证据和系统监控仍需完善。
- 当前限流按单进程客户端 IP 计数，不是分布式限流；尚无完整认证授权和数据权限。
- 已有 35 项后端测试、10 项前端测试及真实四日三通道一致性、Flink Savepoint 恢复验收；这些数字属于 `v0.3.2` 基线，后续变更必须重新运行。
- v0.3.3 阶段 A～E 已完成存储迁移、ClickHouse 双读、Redis 缓存、默认容器、Flink、全量对象、三通道、页面、故障及干净源码与空卷复验，当前回归为后端 57 项、前端 10 项，分支覆盖率 73.27%。用户体验与发布已完成；本版本按用户要求暂缓实施。
- 当前没有可持续的浏览器 E2E 或正式性能报告；已有容器故障注入和 Redis 停服验证，但未实测前不得宣称达到赛题性能指标。

## 3. 范围与非目标

### 范围内

1. 按真实职责拆分数据、特征状态、预警服务，保留清晰的 API 和领域边界。
2. 评估并按需引入 API Gateway，建立 JWT/OAuth2 认证、数据权限、分布式限流和缓存治理。
3. 实现 Caffeine 本地缓存与既有 Redis 的分工，完成可配置预警规则、规则版本和证据关联。
4. 将回放控制、进度、结果和订阅状态持久化，使服务重启后的行为可定义、可恢复。
5. 完善回放看板、状态热力图、预警证据链和系统运行监控。
6. 建立结构化日志、指标、追踪、健康检查和告警规则。
7. 完成性能基准、Flink 逐日回放优化、压力测试与故障恢复演练。
8. `v1.0.0` 的全部赛题合规门槛统一按 [v0.3.x 阶段计划](v0.3.x-plan.md#8-v100-正式版合规门槛) 验收，不能只完成本版本范围就宣称正式合规。

### 非目标

- 不为追求服务数量而把每个函数拆成网络服务，不引入无实际收益的注册中心或消息链路。
- 不改变“数学模型判断、确定性规则预警、LLM 只解释”的职责。
- 不让前端隐藏按钮替代后端权限，不把用户 ID 或角色放在可伪造请求头中直接信任。
- 不用缓存或异步化返回陈旧、跨会话或未来日期的数据。
- 不在本版本承诺多地域容灾、自动交易或完整 LLM 助手。

## 4. 服务与数据边界

### 4.1 演进顺序

先从现有 FastAPI 应用提取真实路由和应用服务，形成可独立测试的模块；再以稳定契约为边界拆出进程。每一步都保持现有 API 可用，不在一次改动中同时替换存储、模型、网关和前端协议。

建议边界：

| 服务 | 拥有的事务与数据 | 对外能力 | 不应越界 |
| --- | --- | --- | --- |
| 数据服务 | 文件目录、导入批次、原始/标准化记录查询、质量报告 | 数据概览、分页、标签筛选、证据定位 | 计算市场状态、修改预警规则 |
| 特征与状态服务 | 特征、模型版本、状态历史、回放可见历史与计算会话 | 当前/历史状态、特征、回放控制与结果订阅 | 直接改原始文件、伪造文本证据 |
| 预警服务 | 规则版本、预警实例、处理状态与证据关联 | 预警查询、规则管理、证据与状态流转 | 让 LLM 自由改变等级或数值特征 |
| 用户与权限能力 | 用户、角色、数据范围、会话/令牌元数据 | 认证、授权检查、用户管理 | 保存行情副本或参与模型计算 |

共享 ID、事件结构和错误码通过稳定契约管理。`market_core/` 仍不依赖 Web 框架、网关、数据库或服务客户端；跨服务调用设置超时、重试预算和幂等键，禁止无界重试形成重试风暴。

### 4.2 API Gateway 评估

先验证单入口是否确有需求，再决定使用成熟网关还是保留边界清晰的 FastAPI 入口。评估项包括：

- 统一 TLS/路由、认证、限流、请求大小、超时和 CORS。
- WebSocket 鉴权、长连接和背压支持。
- 与现有 REST、GraphQL、OpenAPI 的兼容性。
- 本地开发是否可绕过网关直连单服务，运维复杂度是否值得。

网关不是业务规则的存放地。无网关时也必须在服务端执行相同授权，不能依赖网络拓扑假定内部请求安全。

### 4.3 回放状态与通信

- 回放会话、运行 ID、通道、配置、当前事件日期、位点/进度和结果索引持久化；内存只作加速。
- 明确定义服务重启时对运行中会话执行恢复、暂停还是失败标记，不能让前端永远停留在“运行中”。
- WebSocket 只推送快照和增量结果；断线重连通过会话 ID 与序列号补拉，不重复执行模型。
- 本地、Kafka、Flink 通道实现同一应用契约；本地默认，Kafka/Flink 按需启用，不让 Flink 阻塞日常开发和其他页面。
- 跨服务事件带会话、运行、事件时间、模式版本和血缘 ID；结果顺序由事件日期及序列保证，而非依赖网络到达顺序。

## 5. 认证、权限、限流与缓存

### 5.1 认证授权

- 提供安全的本地账号引导流程及可替换的标准身份方案；密码只保存强哈希，令牌有签发者、受众、过期时间和撤销策略。
- 初始角色建议为只读观察者、分析人员、管理员；具体权限用服务端策略表定义，默认拒绝。
- 数据权限至少覆盖数据源/资产范围、规则修改、回放创建、用户管理和运行运维接口。
- REST、GraphQL、WebSocket 使用同一授权语义；长连接在令牌过期、权限撤销时按明确策略断开。
- 对登录、权限变更、规则修改和回放控制记录审计，不记录密码、令牌、API Key 或正文中的敏感配置。

### 5.2 分布式限流与缓存

- 使用 Redis 原子操作实现共享限流，按用户/客户端、接口类别和成本配置额度；返回明确剩余量与重试时间。
- 对计算昂贵的回放创建、导出和查询设置独立配额及并发上限；WebSocket 增加连接数、订阅数和消息级限制。
- Redis 不可用时按接口风险选择受限降级或 fail-closed，管理接口不得静默放开限制。
- 缓存键包含租户/权限范围、查询参数、数据与模型版本；写更新后失效，TTL 只作兜底。
- 权限检查先于受权限影响缓存的复用，防止跨用户或跨数据范围泄漏。

## 6. 前端与运行监控

### 6.1 回放看板

在现有控制条和事件计数基础上增加：

- 会话/运行标识、通道、模型版本、当前事件日期、实际处理时间和恢复状态。
- 生产、消费、去重、重试、位点、窗口输出、迟到事件及积压等真实指标。
- 各阶段耗时与失败原因；无数据时显示未知或不可用，不填造零值。
- 结果证据可回到当日输入、窗口边界、特征和模型版本。

### 6.2 状态热力图与预警证据

- 状态热力图按日期、资产/特征或状态维度提供一致图例、空值和样本量说明。
- 预警详情显示触发规则版本、阈值、实际值、历史分位数、事件时间、关联特征和原始证据链接。
- 状态切换、波动与相关性异常分别解释，不把统计贡献描述成因果。
- 证据数据来自真实 API；长文本按需分页，HTML 继续安全展示，不在列表一次加载整库。

### 6.3 系统监控

- 结构化日志带请求 ID、会话/运行 ID、服务和事件时间，统一错误码，不输出敏感负载。
- 指标覆盖请求延迟/错误、WebSocket 连接、Kafka 消费积压、Flink 作业与检查点、数据库/缓存/对象存储健康及资源使用。
- 关键链路通过请求 ID、运行 ID 或兼容的追踪标准串联；采样不能改变业务处理。
- `/health` 区分进程存活与依赖就绪，依赖慢或不可用时有超时和明确状态。
- 告警针对持续异常和用户影响设置，避免把单次重试直接当系统故障。

## 7. Flink 性能专项

### 7.1 已知现象与假设

当前小批量逐日回放增加了 Kafka 传输、Flink 窗口、水位线推进、事务输出、后端消费和检查点等开销；单节点没有分布式并行收益。现有逐日等待可能使多日输入无法充分流水化。上述是待测量验证的假设，不预先认定某一个组件就是瓶颈。

### 7.2 先建立可复现基准

使用同一机器、同一日期区间、同一份输入和同一模型，分别测量本地、Kafka、Flink：

- 首个结果延迟、逐日耗时、整轮回放墙钟时间和吞吐量。
- 生产发送、broker 等待、水位线/窗口关闭、事务提交、结果轮询、模型计算各阶段耗时。
- CPU、内存、GC、网络/序列化、检查点大小与时长、Kafka 消费滞后。
- 冷启动与热运行分开；至少重复多轮并报告中位数、p95 和波动，不能只选最快一次。

输出机器、数据规模、并行度、检查点间隔、批大小、代码提交和配置，确保结果可复现。

### 7.3 优化顺序与正确性护栏

1. 复用连接和消费者、减少无意义轮询/固定等待、批量拉取和减少重复序列化。
2. 在保留会话可见历史和逐日结果顺序的前提下，允许多日事件生产、窗口计算与模型处理形成有界流水线。
3. 根据测量调整检查点、事务与窗口配置；不得为提速直接关闭检查点、提交未处理位点或忽略迟到事件。
4. 控制事件仍需推进有限历史的水位线，不制造额外交易日；优化后首日之前历史与当日可见性保持不变。
5. 并行化以会话/运行和日期依赖为边界，不能让同一回放的未来结果提前进入模型。
6. 只有测量证明 Python 模型成为瓶颈后，才优化模型或缓存可复用训练状态；不得在 Java 中另写一套算法。

每轮优化必须同时通过固定四日三通道一致性、乱序/迟到、暂停继续、重开、故障恢复和保存点测试。性能提升与结果变化不能混为一次不可解释的改动。

### 7.4 性能验收表达

先形成基线再设量化目标。报告同时列出正确性、延迟、吞吐、资源和恢复结果，不用“实时”“高吞吐”等形容词代替数据。若小批量 Flink 仍慢于本地，应如实说明场景与取舍，并验证其在持续大规模事件流中的扩展性，而不是隐藏本地基准。

## 8. 实施顺序

1. **契约与观测先行**：提取路由、定义错误/事件契约、补阶段计时和结构化日志，建立性能基线。
2. **会话持久化**：迁移回放控制与结果索引，验证重启、断线和重复请求。
3. **服务拆分**：按数据 → 特征状态 → 预警的顺序拆分，逐段回归；评估网关后再接入统一入口。
4. **安全治理**：认证、角色与数据权限覆盖所有协议，再增加分布式限流和权限隔离缓存。
5. **页面完善**：回放运行看板、热力图、预警证据与依赖状态，保持加载和错误状态清晰。
6. **性能与恢复**：执行 Flink 专项、压力与故障演练，形成可复现报告。
7. **完整验收**：自动化、真实 API、Chrome、Compose 和回退流程全部通过后，才请求用户体验并标记版本完成。

允许将性能测量与服务拆分并行准备，但不得在未固定基线时同时改多处导致无法归因。

## 9. 配置与兼容策略

- 新旧路由通过适配层兼容，变更字段有 schema 版本；前端不依赖内部服务地址。
- 服务发现、网关、Redis、身份提供方均有显式配置和无密钥示例；默认开发模式不暴露公网管理接口。
- 数据库迁移遵循 `v0.3.3` 的版本与回退策略，服务滚动升级不假设所有实例同时更新。
- 新增指标、日志和鉴权配置可灰度启用；出现兼容性问题时切回已验证单体组装，而非关闭权限检查。
- 保持本地直连和精简开发模式，完整 Kafka/Flink/网关只用于对应链路验收。

## 10. 测试与验收

### 功能与安全

- 服务契约、超时、幂等、重试、断路/降级和错误传播测试。
- 未登录、过期令牌、越权角色、跨数据范围访问、WebSocket 鉴权和权限撤销测试。
- 多实例共享限流、缓存权限隔离、更新失效及 Redis 故障测试。
- 回放跨服务重启、重复创建、暂停继续、断线补拉、位点恢复和旧消息隔离测试。
- 前端验证真实加载、空状态、错误、长证据分页和运行指标，不只用 mock 验收。

### 性能与容量

- 固定数据规模下对本地/Kafka/Flink、关键查询、WebSocket 和多用户并发建立基准。
- 通过逐步升压寻找饱和点和错误拐点，记录 p50/p95/p99、吞吐、资源和积压恢复时间。
- 测试大分页限制、昂贵标签交集、长回放、重复连接与突发请求，验证限流和背压。
- 性能测试不得使用伪造市场结论；计算结果仍与基线一致。

### 故障恢复

至少演练：特征状态服务重启、预警服务不可用、Kafka broker 重启、Flink 作业 Savepoint 恢复、Redis 丢失、ClickHouse/MySQL 短暂不可用及网关重启。

每种故障记录检测时间、用户表现、数据是否重复/丢失、恢复步骤、恢复时间和未完成事项。单节点环境不能据此宣称高可用。

## 11. 回滚方案

- 保留可运行的单体 API 组装与前端契约，通过配置切回已验证服务路径。
- 新服务以只读或影子流量先行；切换写路径前固定会话和权限数据版本。
- 网关故障可恢复直连受控内网入口，但认证与授权不能因此绕过。
- 性能优化按独立开关或小步提交引入，异常时恢复上一配置；Savepoint、位点和持久会话不随回滚删除。
- 回滚后核对未完成回放、预警处理状态和审计记录，防止双路径同时推进同一会话。

## 12. 风险与控制

- **分布式复杂度反噬开发**：模块先行、按边界拆分、保留本地模式。
- **跨服务结果不一致**：版本化契约、幂等、顺序保证、血缘与一致性测试。
- **权限或缓存泄漏**：默认拒绝、全协议授权、缓存键包含权限范围。
- **指标很多但无法定位**：先定义链路和运行 ID，再采集高价值指标，控制标签基数。
- **为速度破坏正确性**：性能变更必须重跑时间口径、三通道和容错验收。
- **服务重启产生重复回放**：会话持久化、运行 ID、幂等创建与单一推进者。
- **测试环境结论夸大**：报告硬件、规模和限制，不将单节点结果描述为生产高可用。

## 13. 交付物与完成定义

交付包括服务契约与拆分实现、网关评估及必要实现、认证授权与审计、分布式限流/缓存、持久回放、前端看板与证据、监控指标和运行手册、性能与故障恢复报告、完整测试和回退说明。

只有所有计划能力经过真实服务、真实页面、部署与故障场景验证后，才能将 `v0.3.4` 标记完成。任何未实测指标或未恢复场景必须保留为明确待办，不得以任务书或界面占位代替实现。
