## 范围与基线

本批不重复已验收的普通暂停继续、从头重开、断线补拉和三通道一致性，只处理 broker 重启、计算租约丢失、进程异常终止与遗留 Flink 作业。

真实基线使用独立回放数据库、原始行情只读挂载和实际 Kafka/Flink 容器：

- Kafka broker 在首日结果保存后实际重启约 2.969 秒，现有客户端自行恢复；三日结果序列严格为 1、2、3，无重复或跳日。因此不另加一套 Kafka 恢复算法。
- 强制终止 Flink 回放后端后，旧作业仍为 `RUNNING`。原实现恢复时新旧两个同会话、同运行作业同时存在；三日结果虽完成，但旧作业无人接管，恢复链路也没有把已保存 Savepoint 传给新作业。

原始报告位于忽略目录 `server/data/benchmarks/replay-fault-kafka-baseline.json`、`replay-fault-flink-baseline.json`。

## 实现

- `FlinkJobManager` 通过 `/jobs/overview` 发现作业，只接受完全匹配 `MarketLens event-time daily windows {session_id}/{run_id}` 的非终态作业。不得按模糊名称清理其他会话、其他运行或外部作业。
- 只有在会话取得新计算租约并准备启动新作业时，才停止该会话和运行的旧作业；按作业开始时间依次停止并生成 Savepoint，新作业使用最新有效 Savepoint。
- `ReplaySession` 将持久化 Savepoint 传给新建的 Flink 通道；正常恢复和崩溃接管使用同一参数链路。
- 回放事件统计增加 `stale_jobs_stopped`，通道耗时增加 `stale_job_stop_ms`；页面显示“遗留作业清理”数量和耗时。
- `compose.flink.yaml` 同时给实际持有回放管理器的特征服务开启 Flink，不再只给远程代理主后端开启。
- `server/benchmarks/replay_fault_acceptance.py` 固化真实 Kafka 重启、Flink 进程崩溃和独立 Redis 租约丢失演练，检查结果序列与外部作业终态。连接重建期间的瞬态断开会重试直到明确超时，不把单次断网当作业务恢复成功。

## 边界

崩溃后遗留作业在下次取得该会话计算租约并恢复时清理，不宣称进程崩溃瞬间终止外部作业，也不在启动时全局自动清理整个集群。协作式租约仍不是 CPU/内存硬隔离、active-active 路由或分布式 exactly-once；Kafka/Flink 仍为单节点验证环境。

## 真实复验

新镜像使用独立回放数据库和独立 Redis，不修改正式身份库：

- Kafka broker 重启 3.485 秒后，回放完成，三日结果为 1、2、3，无重复或跳日。
- 独立 Redis 在运行中即时停止，租约丢失后暂停在已保存第 2 日，原 Flink 作业停止；Redis 恢复后继续，最终 4 日序列完整，活动遗留作业为 0。
- 强制终止回放进程后确认旧作业仍在运行；重新启动并恢复后，旧作业被清理，恢复期间只有新作业运行，`stale_jobs_stopped=1`。新作业检查点 `restored=1`，恢复来源为旧作业的 Savepoint；最终三日序列完整，活动遗留作业为 0。
- 复验报告位于忽略目录 `server/data/benchmarks/replay-fault-kafka-fixed.json`、`replay-fault-lease-loss.json`、`replay-fault-flink-fixed.json`。
