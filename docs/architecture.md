## 2. 项目定位与边界

项目定位为：

> 以数据管道和市场状态模型为核心，以 Web 监控平台为交付主体，以 LLM 投研助手为增强模块。

核心业务链路为：

> 状态判断 → 预警决策 → 分析建议

- 状态判断：识别趋势、波动、风险偏好和资产联动等市场环境。
- 预警决策：根据可配置规则和异常检测结果，决定是否预警及预警级别。
- 分析建议：解释判断依据，关联历史时期、新闻和宏观事件，给出后续关注点。

第一版不以自动交易、多 Agent 自由协作或通用 RAG 聊天应用为主体。资产配置只能作为后续受约束的辅助分析能力，不由 LLM 自由生成数值权重。

## 3. 设计原则

1. 数据平台是地基，市场状态模型是核心，Web 平台是主要交付。
2. 数值特征与状态由数学模型计算，预警由确定性规则和异常检测产生。
3. LLM 负责文本结构化、证据整合和自然语言解释，不直接篡改核心结果。
4. 离线训练与在线识别分离，历史验证严格避免未来数据泄漏。
5. LLM 是可替换、可降级的增强模块，不成为核心链路的单点依赖。
6. 优先跑通完整闭环，再增加 RAG、资产配置和其他创新功能。

## 5. 核心处理流程

1. 多源适配器读取行情、指标、事件与文本，保留来源文件、原始日期和必要的采集时间。
2. 原始文件与非结构化内容保存到 MinIO，元数据写入 MySQL，结构化记录进入后续数据链路。
3. Kafka 按数据类型传递事件，解耦接入与计算，并支持失败重试。
4. Flink 按事件时间完成清洗、标准化、日窗口聚合和特征更新。
5. 在线模型加载已训练的指定版本，输出市场状态和主要判断依据。
6. 规则引擎结合状态变化与异常检测结果，生成可解释的预警。
7. 特征、状态和预警写入 ClickHouse，热点结果进入 Redis，并通过 WebSocket 推送。
8. LLM 按需查询状态、特征、预警和相关文本，生成摘要不参与实时计算关键路径。

## 6. 模块职责

### 6.1 数据接入层

- 为不同文件类型提供独立适配器。
- 对大型 CSV 使用标准解析器流式读取，处理引号与内嵌换行。
- 对 Excel 处理全部目标 sheet。
- 检查完整性、一致性、时效性和记录数。
- 保存导入批次、来源、失败原因与重试状态。
- 所有原始文件必须入库，派生数据与原始层分离。

### 6.2 实时处理层

- 使用 Kafka 解耦数据生产与消费。
- 使用 Flink 完成清洗、窗口聚合、特征计算、状态识别和预警。
- 保留事件时间，处理乱序和迟到数据时明确口径。
- 配置 Checkpoint/Savepoint，支持故障恢复。
- 不在低延迟关键路径中同步调用 LLM。

### 6.3 模型层

离线训练负责历史特征构造、特征选择与降维、模型训练、状态画像、回测和模型版本登记。

在线识别只使用当时可得的数据和已登记模型，输出状态、置信度或相似度、模型版本及主要贡献特征。训练和回测按时间切分，不能使用当时尚未公布的宏观值或未来文本。

### 6.4 存储层

- MySQL：数据目录、导入批次、用户权限、预警规则、特征元数据和模型版本。
- ClickHouse：标准化行情、宏观序列、特征、状态、预警和回测等分析型时序数据。
- Redis：热点查询、热特征、实时推送所需的临时状态与限流信息。
- MinIO：原始文件、研报摘要和其他非结构化对象。

存储设计需进一步落实 ODS/DWD/DWS/ADS 分层、时序分区、索引和生命周期策略。

本地默认实现使用 SQLite：`source_files` 保存文件目录、指纹、状态和质量，`source_records` 保存分页可查询的原始 JSON 负载，`source_daily_stats` 与 `source_fields` 保存日期统计和字段目录，`source_record_tags` 与 `source_tag_stats` 保存确定性标签及计数，`import_batches` 记录导入批次。大型 CSV 分批写入，未变化文件跳过重导；标签仅用于检索，不参与市场状态判断。SQLite 同时保留模型快照和迁移基线，原始导入尚未完全移除该暂存层。

`v0.3.3` 阶段 E 已增加显式 `STORAGE_MODE=local|distributed`：distributed 目录主读使用 ClickHouse，本地仍默认 SQLite。`online_publish` 先归档 MinIO 对象并登记 MySQL 元数据，再将单个来源的新代次记录、标签和统计写入 ClickHouse，完成内容摘要与计数核对后才更新发布指针。六个生效视图只读当前代次，失败保留旧版；多文件批次不是单一跨库事务，旧代次生命周期待后续落实。Redis 只缓存可重建查询并回到同一显式主存储。部署文件和详细验收边界见 [阶段 E 部署与验收](stage-e-deployment.md)。

### 6.5 服务层

- API Gateway：统一入口、认证、限流与路由。
- 数据服务：数据目录、行情、指标、文本和质量报告查询。
- 特征与状态服务：特征、当前状态、历史状态和模型解释查询。
- 预警服务：预警列表、规则配置、处理状态和回测结果。
- 实时推送服务：通过 WebSocket 推送状态变化与预警。
- 用户与权限能力：认证和数据权限，可作为独立服务或边界清晰的共享模块。

提供 RESTful API、GraphQL、WebSocket 和 OpenAPI 文档。服务数量以职责清晰和可维护为准，避免无意义拆分。

### 6.6 LLM 分析助手

提供每日市场摘要、状态切换解释、预警说明、相关文本检索和自然语言问答。

助手只能通过受控接口获取数据，例如：

```text
get_market_state(date)
get_feature_changes(date)
get_active_alerts(date)
get_related_events(date)
search_research_documents(query)
```

LLM 不得直接修改原始行情、特征、状态标签、已触发预警或模型版本。其不可用时，数据接入、状态识别、预警和看板仍须正常运行。

### 6.7 Web 平台

当前工作区 Web 平台包含以下页面；该终端化批次已获用户明确本地提交授权，版本保持 `0.3.4`，不补记页面体验结果：

1. 终端首页：紧凑的真实市场状态、数据规模、研究边界和核心工具入口，不再使用长营销页面。
2. 市场总览：资产目录筛选、真实历史主图、当前状态、标准化偏离和近期预警，采用三栏研究布局。
3. 市场状态分析：状态时间轴、120 日热力图和状态记录；聚类距离权重与标准化偏离均不作为预测正确率或因果贡献。
4. 历史回放：选择事件日期范围，控制开始、暂停、继续、倍速和重开，查看逐日真实计算的状态、输入证据、特征和新增预警；技术耗时按需展开。
5. 特征分析：收益率、波动率、动量、相关性、趋势、样本量和历史曲线，明确区分展示特征与聚类输入。
6. 预警中心：高密度预警表格、级别筛选、可配置确定性规则、历史版本恢复和证据抽屉；抽屉支持 Escape、焦点循环和原触发按钮焦点恢复，预警效果回测仍待实现。
7. 数据中心：按类型展示用途说明、时间覆盖、预聚合记录量趋势、字段目录和最新内容；新闻、社媒、公众号和研究摘要使用纯文本友好视图，原始文件与字段保留在核对区。最多组合 5 个标签，支持并集、交集、标题、日期和文件筛选；记录与文件均由服务端分页，原始文件目录仅在展开后加载。
8. 系统管理：账号权限、审计记录和系统监控分别使用 `#/accounts`、`#/audit`、`#/system`，与其他页面共享导航、权限和错误契约。

首页只请求轻量摘要，市场列表在进入市场页面后加载，数据中心与历史回放独立加载，资产价格序列只在市场总览需要时加载。回放页通过 REST 控制会话，通过 WebSocket 接收状态快照和逐日结果；离开页面不会终止后端会话，返回后重新订阅当前会话。普通折线图由 `Chart` 注册，状态散点和热力图由 `RegimeChart` 注册，`EChartsCanvas` 统一处理尺寸监听和销毁。全部主要页面按权限使用哈希深链，支持刷新和浏览器后退；全局回到顶部继续使用 `requestAnimationFrame` 和 `prefers-reduced-motion`，切换页面时重置到顶部。

## 7. 历史数据回放

`v0.3.0` 已实现 Python + SQLite 数据之上的本地真实历史回放；`v0.3.1` 已增加真实单节点 Kafka 事件通道；`v0.3.2` 已增加真实 Flink 日窗口与容错：

- 回放会话按资产原始事件日期逐日读取输入；不同资产保留各自交易日历，某日无观测时不伪造行情。
- 每个会话独立保存可见历史。首日之前的数据用于滚动窗口和模型预热，当日输入到达后才追加当日记录，不读取未来记录。
- 特征通过现有确定性函数重新计算；状态通过连续 walk-forward 会话逐日识别，训练切片排除识别日；预警使用此前状态历史和当日结果生成。本地、Kafka 与 Flink 通道共用同一计算器。
- 每条结果保存事件时间、UTC 实际处理时间、可见输入范围、当日输入条数、资产代码、特征、状态、预警和模型版本。
- 时钟支持待开始、运行、暂停、完成和失败，支持范围选择、0.5/1/2/5/10 倍速及重开。暂停等待正在计算的日期结束后生效，继续通过事件唤醒后台任务；完成状态只在最后一天结果保存后发布。
- REST 路径为 `/api/replay/calendar`、`/api/kafka/status`、`/api/flink/status` 与 `/api/replay/sessions*`，新 WebSocket 为 `/ws/replay/{session_id}`；旧 `/ws/replay` 暂时保留作回归对照。
- 当前回放输入仅为资产行情。宏观、事件和文本已经入库但尚未进入回放计算，接入时必须按实际公布或发布时间确定可见性，不能把统计期当成发布日期。

### Kafka v0.3.1 事件口径

- 主题为 `marketlens.replay.days.v1`，当前单分区、单副本；key 为 `event_date`，value 为 `market.replay.day.v1` JSON。每个事件包含一个交易日全部资产观测，以及 `schema_version`、`event_id`、`session_id`、`run_id`、`event_time`、`replay_time`、`source` 和 payload。
- `aiokafka` 生产者使用 `acks=all` 和幂等发送；消费者组按会话和运行标识隔离，从最早位点读取并过滤当前运行，关闭自动提交。
- 消费者按 `event_id` 去重，非当前期望日期的消息先缓存；临时 `KafkaError` 按配置退避重试。模型处理成功后调用 `ack`，只提交各分区已连续处理完成的偏移，乱序缓存不会提前提交。
- 重开产生新的 `run_id` 和消费者组并重新发送所选历史，防止旧位点导致新回放无数据。Kafka 仅承担事件传输，SQLite 继续保存原始档案；会话、逐日结果、恢复状态和幂等操作由 `ReplayStore` 持久化，内存只保留当前运行对象。
- 共享主题中的其他运行消息会跳过并提交，因此页面“位点提交”次数可能大于当前会话消费事件数；它不是当前模型的处理天数。

### Flink v0.3.2 窗口与容错

- `flink/` 是独立 Java 17 源码和 Maven 工程，运行环境为 Flink 2.2.1 + Kafka Connector 5.0.0，不改变 `market_core` 的算法边界。
- 每次 `run_id` 由后端通过 Flink REST 启动独立作业和消费者组。source 先过滤当前会话与运行，再分配事件时间和水位线，避免其他历史回放或旧控制事件推进本运行的时间。后端等待作业进入 RUNNING 且首个检查点完成后才生产行情，防止 latest 位点尚未建立时丢失首日。
- Kafka source 使用事件时间和最多 2 天乱序的水位线，1d 滚动事件时间窗口按 `session_id + run_id + event_date` 分组，允许迟到 2 天，更晚事件写入 `marketlens.replay.late.v1`。不同频率或没有观测的资产日期不补齐。
- 窗口按 `event_id` 去重，同日不同 ID 冲突和同资产重复直接报错；输出保留原始观测并增加窗口起止、输入记录数和资产数。日窗口不计算跨资产均值，滚动收益、波动率、动量、相关性及 PCA/KMeans 继续由 Python 执行。
- 每轮回放结束发送 `market.replay.control.v1`。控制事件以最后事件日期加 3 天作为内部控制时间，在最多 2 天乱序口径下推进水位线并关闭最后窗口；它在窗口前过滤，不构造额外行情或交易日，也不把历史行情时间改为处理时间。
- 每 5 秒执行 Exactly-Once 检查点，Kafka sink 使用事务输出；后端以 `read_committed` 读取 `marketlens.features.days.v1`。算子具有稳定 UID，检查点和 Savepoint 均保存在项目运行目录。正常结束只按作业 ID 停止本运行并生成 Savepoint，不取消其他会话。
- 已验证同一集群连续运行、相同与不同日期范围、暂停继续、同会话重开、四日三通道 `1e-12` 容差一致性、乱序去重、超迟分流和 Savepoint 恢复。当前仅为单 JobManager/TaskManager 验证环境，不是高可用集群，也未形成竞赛性能验收报告。

### v0.3.4 首批契约与观测（实施中）

- REST 已按 system、market、data、replay 提取到 `server/app/api/`，保持既有 URL 与 `detail` 兼容；错误响应新增稳定 `error.code` 和 `error.request_id`，成功与错误响应均返回 `X-Request-ID`。GraphQL 和 WebSocket 仍由主应用组装，不代表已经拆成独立微服务。
- JSON 请求日志记录路由模板、状态码、耗时和请求 ID，不记录查询参数或正文。`/api/system/metrics` 提供当前进程的路由 p50/p95/p99、错误数、WebSocket 连接和回放会话数；它不是跨实例聚合指标。`/api/health` 保持存活检查，`/api/health/ready` 检查市场快照和目录可读性。
- 回放快照增加 `run_id`、`flink_job_id`、`savepoint_path` 和 `timing`，分别记录模型初始化、通道初始化、逐日输入等待、模型计算、结果确认，以及 Kafka 生产、消费等待、位点提交、Flink 作业就绪和 Savepoint 停止耗时。回放页只展示真实测量值，无数据时显示未知。
- 首批基准发现同一 Flink 作业连续回放的全局水位线缺陷，现已通过每运行独立作业和过滤后水位线修复。连续两轮均产出全部正常消息且迟到消息为 0；真实 Chrome 已核对最终运行面板。独立作业增加启动与首检查点等待，小数据下仍慢于本地，性能优化不能以恢复共享全局水位线为代价。

### v0.3.4 回放持久化与恢复

- `ReplayStore` 在现有 SQLite 中分别保存会话快照、逐日结果、幂等操作和当前会话指针。结果与快照同事务提交，已完成位置只包含成功保存的结果日；服务关闭时回滚未完成游标。
- 未完成会话在后端重启后进入可恢复暂停。继续时保留运行 ID，先按原始行情重建已保存日的模型内部状态，再从下一未保存日运行；Flink 创建新作业 ID。模型重建需要实际计算，不宣称高可用或瞬时恢复。
- `/api/replay/sessions/{id}/results?after=N&limit=100` 提供结果补拉，WebSocket 逐日消息带序列号。前端自动重连、忽略旧序号，并用重开代次阻止上一轮补拉污染新结果。创建和控制操作支持 `Idempotency-Key`。
- 真实 Docker 重启已验证首日保留、三日序列完整、运行 ID 不变和新作业 ID；真实 Chrome 已验证恢复展示及刷新后的结果补拉。详见 [回放持久化与恢复](v0.3.4-replay-persistence.md)。

### v0.3.4 Kafka/Flink 异常治理

- Flink 恢复在取得新计算租约后，通过作业全名精确匹配当前 `session_id + run_id` 的非终态旧作业，逐个停止并生成 Savepoint，再把最新有效 Savepoint 传给新作业。不得清理其他会话、其他运行或外部作业。
- 页面展示遗留作业清理数量和实际耗时。可选 Flink 编排同时配置主后端与实际执行回放的特征服务。
- 进程崩溃后的作业在下次恢复该会话时接管，不是崩溃瞬间终止；不做全集群自动清理。详见 [异常治理与故障演练](v0.3.4-replay-faults.md)。

### v0.3.4 数据服务独立部署

- `app.data_service:app` 只组装数据目录、健康和进程指标接口，不加载市场模型或回放管理器。`DataCatalogService` 独占目录查询与 Redis 缓存组装，主后端通过 `RemoteCatalogClient` 复用同一 REST 契约。
- `DATA_SERVICE_URL` 为空时保留既有本地单体路径；配置后由主后端通过有界超时的内部 HTTP 调用数据服务，不自动重试。请求 ID 透传，失败对原接口返回 503 和 `data_service_unavailable`，不暴露内部地址或存储异常。
- 前端仍只访问原主后端和 Nginx 同源接口，REST、GraphQL、WebSocket 与回放计算边界不变。Compose 增加 `data-service`，主后端等待其 readiness；特征状态和预警尚未拆成独立进程，不能称为完整微服务体系。
- 真实 Compose 验收中，数据总量、类型概览、标签、文件分页和多标签记录查询五组主服务/数据服务响应逐字一致，GraphQL 保持可用。停止数据服务后数据接口与 readiness 返回 503，市场摘要继续返回 200；重新启动数据服务后无需重启主后端即恢复。该结果证明进程边界和故障隔离，不代表服务间鉴权或高可用已经完成。

### v0.3.4 特征与状态服务独立部署

- `app.feature_service:app` 复用同一应用组装，独立持有 `MarketService`、`ReplayManager`、模型快照和回放会话；通过 `DATA_SERVICE_URL` 调用数据服务，不直接拥有目录主读。
- 主后端设置 `FEATURE_SERVICE_URL` 后不再创建第二份模型或回放管理器。市场和回放 REST 由有界超时代理转发，保留查询参数、正文、幂等键、状态码和错误结构；`/ws/replay*` 双向中继并传递上游关闭码。
- GraphQL 在主后端组合特征服务的 `assets`、`latestState` 与数据服务的 `sourceSummary`；OpenAPI 复用特征服务完整 schema。Nginx 和前端仍只访问主后端，不要求浏览器知道内部服务地址。
- 这是现有 FastAPI 入口的兼容代理，不是另起一套通用 API Gateway，也不改变模型、事件时间或三通道算法。历史预警查询随后由独立预警服务承担。
- 真实 Compose 已核对五组市场/回放查询一致、GraphQL 与完整 OpenAPI；两日回放通过主后端 WebSocket 产出序列 1、2，REST 补拉一致，不存在会话保持 4404，Nginx 旧 WebSocket 对照可用。停止特征服务时市场与回放为 503、数据目录为 200；恢复后无需重启主后端。三日回放在首日后重启特征服务，恢复原运行 ID 并完成序列 1、2、3，模型重建约 13.40 秒。

### v0.3.4 预警服务独立部署

- `app.alert_service:app` 启动时通过 `FEATURE_SERVICE_URL` 读取 `/api/internal/alert-states`，使用 `market_core.models.alerts.generate_alerts` 重建历史预警并独立提供 `/api/alerts`、健康和进程指标。内部输入只含日期、状态标签、波动率和相关性；非有限数值以 `null` 传输并按缺失值处理，避免标准 JSON 序列化 `NaN` 失败。
- 主后端配置 `ALERT_SERVICE_URL` 后只将 `/api/alerts` 转发到预警服务，其余市场与回放请求仍走特征服务。GraphQL、OpenAPI、WebSocket 和前端预警结构不变；未配置服务地址时保留单体路径。
- 逐日回放仍在特征服务内调用同一个纯规则函数，不增加每个交易日的同步网络调用。历史与增量一致性、至少 60 个历史状态日、三类规则、缺失值和空结果均有契约测试；预警服务不是另一套算法实现。
- 真实 Compose 中主后端、预警服务和特征服务最新 1,000 条预警逐字一致，总计 1,127 条历史预警。停止预警服务后预警查询和整体 readiness 为 503，市场与数据目录为 200，主后端 WebSocket 本地回放仍完成且 REST 补拉一致；恢复预警服务无需重启主后端。该结果不代表可配置规则、证据链、服务鉴权或高可用已经完成。

### v0.3.4 回放计算并发与缺失值（已验收）

- 特征服务/单体 ReplayManager 使用独立计算租约池，默认 `REPLAY_MAX_RUNNING=2`；Redis 模式跨进程共享预算，每会话最多一个持有者，local 模式仅本进程。创建会话与订阅不占计算名额，开始/继续/重开先申请；超额 429、Redis 故障 503，保留结构化错误及 `Retry-After: 5`。
- 默认 30 秒租约、10 秒续租；暂停等待实际线程与通道清理后释放。丢租约停在已提交交易日并执行通道清理；SQLite 所有权令牌在写事务中检查，阻止旧持有者覆盖新进度。租约本身不保证进程崩溃瞬间终止外部作业，崩溃接管见异常治理章节；不是硬隔离、active-active 或高可用。
- 前端保留启动被拒绝的待开始会话，以“启动此会话”重试相同 ID。真实 39 资产双进程和 Chrome 两日回放验证通过；Kafka/Flink 崩溃协调已在后续专项覆盖。完整证据、操作与边界见 [计算并发说明](v0.3.4-replay-capacity.md)。
- 回放快照、控制响应、WebSocket 和结果补拉把非有限数值统一为 `null`；新持久化使用严格 JSON，旧记录读取时同样转换。前端以“—”表示缺失且不填零。真实 2015-01-05 回放与 Chrome 已验收，内部模型和时间口径不变。

```text
market_core/
  domain/              # 资产、预警、数据文件与记录领域对象
  ingestion/           # 资产、Excel、CSV、新闻与 Markdown 适配器

  app/feature_service.py # 独立特征状态与回放服务
  app/alert_service.py # 独立历史预警查询服务
  tests/               # 核心、导入、接口与服务契约测试
  config.example.json  # 无密钥配置模板
  config.json          # 本地私有配置，Git 忽略

flink/                 # Java 日窗口作业、Kafka 连接与 Maven 构建

docs/                  # 架构和后续数据、模型文档
```
